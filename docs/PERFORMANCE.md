# Omni Deck 性能调优实录

> 2026 年 9 月底 ~ 10 月初，Steam Deck（16GB 内存、SteamOS / KDE Wayland）上的一轮系统性调优。
> 这份文档按「方法 → 工具 → 案例 → 原则」组织，每个案例都写清楚 **现象 → 怎么定位 → 根因 → 怎么修 → 修完的数据**，
> 数字全部来自实测（不是估算），可以直接拿去讲。

---

## 一、结果总览

| 问题 | 优化前 | 优化后 | 关键手段 |
|---|---|---|---|
| Omni 主进程多联播放换片后的内存 | 一路涨到 **1.5GB**（不回落） | 稳定在 **370~480MB** | glibc 分配器调参（mmap 阈值 + arena 上限） |
| 抖音列表在 Python 里的内存 | **142MB** | **50MB** | 数据结构瘦身：派生字段不存、字符串 intern |
| 抖音列表落盘快照 | **69MB**，每分钟重写 | **19MB**，有增删才写 | 同上 + 消除「伪变化」+ 写盘节流 |
| 网页进程（滚 15 页短视频后） | **696MB** | **241MB** | 图集封面原图 → 360px 缩略图 |
| 冷启动窗口出来前的等待 | **~14 秒** | 去掉了这一段 | 游戏库扫描改按需 |
| 游戏库首次加载 | **1.8 秒**（冷缓存十几秒） | **6 毫秒** | 目录指纹 + 落盘快照 |
| 多联播放时磁盘读 | **~50MB/s** | 播放本身的 1~3MB/s | 打断后台「扫描→通知→刷新→再扫描」死循环 |
| Chrome 冷启动卡、内存高 | History 库 **244MB**、**22 万**条下载记录 | 清空，且不再累积 | 扩展批量清理自己的下载记录 |
| 系统内存紧张时 | Omni 照常跑后台任务 | 自动暂停 / 释放 / 收缩 | PSI 内存压力监测 |

用户侧的直观感受：Omni 整体内存占用下降约 40%，多联放映不再越用越卡。

## 二、方法：每个问题都走的七步

1. **量化现象**：「卡」「内存高」不是问题描述。先变成数字：哪个进程、RSS 多少、读写多少 MB/s、启动每一步几秒。
2. **拆分归因**：一个进程的内存要拆成 匿名内存 / 文件映射 / 交换；一个应用要拆成 主进程 / 子进程；
   一段启动时间要按日志打点拆成每一步。**不拆就只能猜。**
3. **提出可证伪的假设**：比如「是 glibc 的 arena 碎片」——它能被一个实验推翻或证实。
4. **做最小复现实验**：不在用户正在用的实例上动刀，单独起一个实例（独立端口 + 临时状态目录 `OMNI_STATE_DIR`），
   只复现那一个变量（比如只让三个播放器不停换片）。
5. **改一处、测一次**：对照组 vs 实验组，同样的输入，看数字。
6. **验证没改坏**：新旧代码对同样的查询输出逐字段比对；跑界面冒烟测试（`tests/ui_smoke.py`，32 步）；
   边界条件单测（比如断点续传的「传一半断开」「校验不对」）。
7. **留下记录**：提交信息里写清根因和数字（`git log` 就是调优日志），再汇总成这份文档。

## 三、工具箱（全是 Linux 自带或 Python 标准库）

| 想知道什么 | 看哪里 / 用什么 |
|---|---|
| 进程内存构成 | `/proc/<pid>/status`：`VmRSS`（当前驻留）、`VmHWM`（峰值）、`RssAnon`（程序自己 malloc 的）、`RssFile`（映射的 .so / 文件，可丢弃）、`VmSwap` |
| 多进程真实占用（共享库不重复算） | `/proc/<pid>/smaps_rollup` 的 **PSS** |
| 内存块的形态（判断是谁分配的） | `/proc/<pid>/smaps`：按大小分桶统计匿名映射——一堆 64MB 对齐的块 = glibc 的线程 arena |
| 进程 / 线程的磁盘读写 | `/proc/<pid>/io` 的 `read_bytes` / `write_bytes`，隔 N 秒采两次求速率；`/proc/<pid>/task/*/io` 精确到线程 |
| 线程是谁开的 | `/proc/<pid>/task/*/comm`：`gl0` / `traceq0` / `sh0` 是 Mesa 显卡驱动，`ThreadPoolForeg` 是 Chromium，`python` 才是自己的 |
| 打开了哪些文件 | `ls -l /proc/<pid>/fd` |
| 进程归属（系统把它算成哪个应用） | `/proc/<pid>/cgroup` |
| 系统内存压力 | `/proc/pressure/memory`（PSI，内核 4.20+）+ `/proc/meminfo` 的 `MemAvailable` |
| Python 对象占多少 | `tracemalloc`（对比加载前后的 `get_traced_memory()`） |
| Python 时间花在哪 | `cProfile` + `pstats` 按累计时间排序 |
| 网页 / 界面行为 | 离屏 QtWebEngine（`QT_QPA_PLATFORM=offscreen`）驱动真实页面，用 `runJavaScript` 读状态做断言，必要时截一张图 |
| SQLite 里有什么 | 先 `cp` 一份再查（避免锁住正在用的库） |

注意事项：SteamOS 默认 `ptrace_scope=1`，不能 attach 到不是自己子进程的程序（gdb 调 `malloc_trim` 做不了），
所以内存类实验一律「自己起一个实例来复现」。

## 四、案例

### 案例 1：多联播放内存越用越大 —— glibc 的 arena 碎片

**现象**：重启后 9 分钟，Python 主进程 RSS 1.9GB，其中匿名内存 1.58GB。

**定位**
- 按大小给匿名映射分桶：**69 块 2~64MB 的区域共 1.4GB**，地址都是 64MB 对齐 → 这是 glibc 给每个线程开的 malloc arena，不是 Python 自己的对象池（那是一堆 256KB 的小块）。
- 线程有 140 多个（大部分是 Chromium 和显卡驱动的），每个线程都可能拿到自己的 arena（上限 8×CPU 核数）。
- 最小复现：离屏起 3 个 `QMediaPlayer`，每 1.5 秒换一条视频，80 次后 **1.5GB 且不回落**。

**根因**：抖音很多竖屏视频是 1900×3378 的 HEVC，一帧解码缓冲 10~25MB。glibc 的 mmap 阈值是**动态**的——
每释放一次大块，阈值就往上调（最高 32MB）。阈值涨上去以后，这些帧缓冲改从 arena 里分配，释放后碎在里面还不给系统。

**修复**：启动第一步（还没起任何线程）用 `mallopt` 固定 `M_MMAP_THRESHOLD = 1MB`（大块一律 mmap，释放即归还）、
`M_ARENA_MAX = 4`。见 `omni/app.py: _tune_malloc()`。

**数据**：同样的 80 次换片实验，**1.5GB → 370~480MB 且平稳**；真实使用中匿名内存从 1.72GB 降到 ~560MB。

> 能讲的点：区分「内存泄漏」和「分配器碎片」——前者是对象没释放，后者是释放了但没还给系统；
> 判断依据是内存块的形态和 `malloc_trim` 之后能不能降下来。

### 案例 2：磁盘 50MB/s —— 一个「扫描 → 通知 → 刷新 → 再扫描」的死循环

**现象**：多联播放时磁盘读 50MB/s，而三路短视频本身只需要 1~3MB/s。

**定位**
- 抖音列表快照文件（56MB）在 21 秒里被重写两次。
- 读代码：后台重扫完成后**无条件**广播 `library_indexed`；网页收到就请求一次列表；列表接口发现缓存超过 20 秒 TTL，又触发后台重扫……

**根因**：反馈环。每轮都要遍历 5.5 万个文件、读整个元数据索引、重写 56MB JSON。

**修复（第一轮）**：扫描结果跟上一份**逐条比较**（Python 的 dict 列表比较在 C 层，几十毫秒），没变化就不写盘、不广播；TTL 20s → 60s。

**修复（第二轮，后来发现的隐藏 bug）**：比较还是每次都「变了」——因为列表查询接口直接往**缓存里的条目**写了 `liked` / `local_cached` 字段，新扫描的条目没有这两个字段，自然不相等。改成查询返回副本，缓存只读。

> 能讲的点：缓存条目被调用方顺手改掉，会让「变化检测」永远失效。共享数据要么不可变，要么只给副本。

### 案例 3：冷启动等 14 秒 —— 启动路径上做了不该做的事

**定位**：`var/logs/boot.log` 里每步都有时间戳：「HTTP 服务起来」在 0.44s，「开始导入 Qt」在 14.29s，中间只有一个 `registry.scan()`。
`cProfile` 显示它为了给 133 个游戏找主程序，遍历了 **13.7 万个文件**（钢铁雄心 4 一个就 6 万个）。

**修复**
1. **按需**：启动时不扫，打开游戏分区时接口自己扫；按 id 查不到时补扫。窗口不再等这 14 秒。
2. **快照**：原本就有一个「目录指纹」（各分类目录的 mtime + 库清单，毫秒级），只存在内存里。现在指纹和扫描结果一起落盘，新进程指纹对得上就直接读——**1.8 秒 → 6 毫秒**。

**过程中的教训**：第一版快照存进去的指纹是字符串 `"games.flash"`——变量名 `key` 被下面扫描循环里的 `for key, register in ...` 盖掉了。是跨进程测试（「第二个进程应该是毫秒级，结果还是 1.8 秒」）抓出来的。**优化一定要用数字验证，不能看代码觉得对就算完。**

> 能讲的点：启动优化的第一原则是「启动路径上只做必须做的事」；第二是「能缓存的计算，用一个廉价的指纹判断能不能复用」。

### 案例 4：列表瘦身 —— 不存能算出来的东西

**现象**：抖音列表 6.6 万条，Python 里占 142MB，快照 69MB。

**分析**：每条 13 个字段，其中 `thumb_url` / `stream_url` 是两条把中文路径百分号编码过的长 URL，
`title` / `filename` / `size_mb` / `mtime_str` 都能从别的字段推出来；作者名字符串每条一份（一个作者上千条）。

**修复**：内存和快照只存 `platform / rel_path / folder / mtime / size / kind / duration / width / height`，
`folder` 用 `sys.intern` 共享；给网页的完整字段在 `public_item()` 里**按页现算**（一页 60 条，成本可以忽略）。
旧格式快照读进来时自动转换。另外多联「全部平台」频道原来给每条 `dict(it, platform=...)` 拷一份，现在条目自带 platform，直接复用。

**验证**：新旧两个模块读同一份快照，对 5 种查询（全部 / 点赞 / 搜索 / 翻页 / 按作者）逐字段比较输出，**0 差异**。

**数据**：**142MB → 50MB**，快照 **69MB → 19MB**。

### 案例 5：网页进程 —— 一张封面 21MB

**现象**：网页进程（Chromium renderer）首屏 174MB，滚 15 页短视频（198 张卡片）后 **696MB**，平均每张卡片 2.9MB。

**定位**：视频缩略图已经是 360×640（解码 0.9MB），对不上；抽查发现抖音 2 万个图集的卡片封面直接用的是**原图**，
1400×2500 上下，**解码后 10~21MB 一张**。

**修复**：图集封面也走缩略图缓存（第一张缩到 360 宽 WebP），看大图时才加载原图。

**数据**：滚 15 页后 **696MB → 241MB**，首屏 174MB → 122MB。

**配套**：
- 懒加载：启动不再预取漫画 / 小说 / 音声的完整列表，点进分区才加载。
- 定时修剪：离开一个分区 10 分钟没回来，清掉滚动加载出来的卡片，只留首屏那一批；回来就取消计时。
- 实测发现：单纯删 DOM，renderer 的 RSS 只降 10MB 左右——Chromium 释放的内存会先留在自己的分配器里。
  **真正有效的是让每张图本身变小**，修剪更多是防止长时间挂着越积越多。

> 能讲的点：前端内存优化要先算「单位成本」（每张卡片多少 MB），而不是一上来就做虚拟列表；
> 一张图的内存 = 宽 × 高 × 4，跟文件大小无关（98KB 的 JPEG 解码后 21MB）。

### 案例 6：后台任务的写盘节流

**现象**：扩展又下载了一万多条视频，后台在逐个 `ffprobe` 补时长 / 分辨率（1.3 万条要补几十分钟）。
每补一批列表就「变了」，于是每分钟重写一次 70MB 快照。

**修复**：文件有增减 → 立刻写；只是补了元数据 → 最多 10 分钟写一次（元数据本来就在 SQLite 索引里，快照只是冷启动垫底）。

> 能讲的点：区分「结构性变化」和「属性变化」，对后者做节流。

### 案例 7：对系统内存压力做出反应

**做法**（`omni/core/memwatch.py`）：每 5 秒读 `/proc/meminfo` 的 `MemAvailable` 和 PSI 的 `some avg10`。

- 进入「紧张」：可用 < 10%，或最近 10 秒里 ≥ 10% 的时间有进程在等内存。
- 紧张时：暂停后台 `ffprobe` 补元数据（循环里每条前调 `wait_if_tight()`）；`gc.collect()` + `malloc_trim(0)`；
  SSE 广播 `memory_pressure`，网页把等着修剪的分区立刻修剪。
- 解除：可用 ≥ 15% 且 PSI < 2%，**连续 3 次**才算——留回差，避免在阈值附近来回抖。

**验证**：用模拟读数驱动：紧张时后台循环停住、恢复后继续；中间一次回升到 12% 不会提前解除。

> 能讲的点：PSI 比「剩余内存」更能反映真实压力（剩余内存少但没人在等，不算紧张）；阈值要有回差（hysteresis）。

### 案例 8：Chrome 越用越卡 —— 自己写的扩展留下 22 万条下载记录

**定位**：Chrome 主进程 RSS 1.4GB、CPU 93%；`History` 库 244MB；复制出来查 `downloads` 表：**223,850 条**，
99.8% 来自自己写的「抖音创作者作品归档助手」扩展。

**根因**：`chrome.downloads.download()` 每个文件留一条记录，Chrome 从不自动清；启动时全部读进内存。

**修复**（ExtensionForge 仓库）：结束的下载攒够 200 个、或队列跑空时扫一遍，只 `erase` 本扩展发起、已结束、
不在下载中的记录（不删文件）；浏览器启动 / 扩展重载时兜底扫一次。没有「一次删一批」的 API，批量体现在触发时机上。

## 五、顺带完成的：大文件断点续传（面试常考的设计题）

局域网小工具的上传协议（`omni/features/tools/`）：

| 要点 | 做法 |
|---|---|
| 分片 | 前端 `file.slice()`，每块 8MB（经 Cloudflare 时单请求上限 100MB，手机重传代价也小） |
| 内存 | 服务端边读边写 `.part` 文件，每次 1MB，**上传 50MB 文件时服务端内存峰值 43MB** |
| 进度 | 服务端以 `.part` 的字节数为准；每块必须从「已收到的字节数」开始，否则返回真实进度让客户端对齐 |
| 校验 | 每块带 CRC32；整块收齐且校验对上才保留，否则截回块开头、让客户端重发——文件里每个字节都校验过 |
| 续传 | 网络断了退避重试，重试前先问服务端进度；刷新页面后重新选同一个文件（名字+大小+修改时间）从断点继续 |
| 秒传 | 抽样哈希 = sha256(大小 + 开头/中间/结尾各 1MB)；共享文件夹里有大小、哈希都相同的文件就提示「已存在」，**由用户选跳过还是仍然上传**——抽样没覆盖中间，确有误判的可能（实测改中间 1 字节会被判同） |
| 落盘 | 收满后原子 `rename` 进共享文件夹；同名自动改「名字 (1).ext」不覆盖 |
| 下载续传 | HTTP Range（服务端原本就支持），浏览器 / 下载器断了自动接着下 |
| 没做的 | 多块并发上传：局域网单路就能跑满 WiFi，并发收益小，却要维护块位图 |

局域网是普通 HTTP 页面，浏览器不给 `crypto.subtle`，所以 CRC32 和 SHA-256 是手写的 JS；
用 0、55、56、63、64 字节和 3MB 边界等尺寸跟 Python 的 `zlib` / `hashlib` 逐一对过。

## 六、可以复用的原则

1. **先测量，再优化**。每一步都有数字，修完再测一次。
2. **拆开看**：RSS ≠ 真实占用（看匿名 vs 文件映射、PSS）；一个应用 ≠ 一个进程。
3. **找反馈环**：「A 触发 B，B 又触发 A」是后台任务最常见的性能事故。
4. **不存能算出来的东西**；重复的字符串 intern；按页现算展示字段。
5. **缓存要有廉价的失效指纹**（mtime、大小），并且缓存条目不要被调用方修改。
6. **区分结构变化和属性变化**，对后者节流。
7. **启动路径只做必须做的事**，其余按需或后台。
8. **前端先算单位成本**：一张图解码 = 宽×高×4 字节。
9. **对系统状态敏感**：内存紧张时主动让路，阈值留回差。
10. **验证手段要跟上**：新旧输出逐字段比对、跨进程测试、模拟读数驱动、离屏浏览器跑真实页面。
